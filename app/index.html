01

El problema que Docker vino a resolver

Tu código funciona perfecto en tu máquina. Lo mandas a un compañero y explota. Lo subes al servidor y explota distinto. ¿Por qué?

🧩

Dependencias distintas

Tú tienes Node 20, tu compañero Node 16, el servidor Node 14. Cada uno se comporta diferente.

🖥️

Sistemas distintos

Tú en macOS, tu compañero en Windows, el servidor en Ubuntu. Rutas, permisos y librerías cambian.

⚙️

Configuración distinta

Variables de entorno, puertos ocupados, versiones del servidor web. Nada está documentado.

💬
"Pero en mi máquina sí funciona"

La frase más cara de la industria del software. Docker la elimina: si funciona en el contenedor, funciona en cualquier lado donde ese contenedor pueda correr.

02

¿Qué es Docker?

Docker es una plataforma que empaqueta una aplicación junto con todo lo que necesita para ejecutarse —sistema operativo base, librerías, dependencias y configuración— dentro de una unidad estándar y portable llamada contenedor.

La analogía viene del transporte marítimo. Antes, cada mercancía se cargaba de forma distinta: sacos, barriles, cajas sueltas. Al estandarizar el contenedor metálico, dejó de importar qué llevaba adentro: cualquier barco, grúa, tren o camión del mundo podía moverlo igual.

Docker hizo lo mismo con el software. No importa qué hay adentro —Python, Java, una web estática como esta—: cualquier máquina con Docker lo ejecuta de la misma manera.

03

Los 6 conceptos que necesitas

Si entiendes estos seis, entiendes Docker. Todo lo demás son detalles.

📄

Dockerfile

La receta. Un archivo de texto con los pasos para construir tu imagen.

Ejemplo: "parte de Nginx, copia estos archivos, escucha en el puerto 80".

📦

Imagen

El paquete congelado que resulta de cocinar la receta. Es inmutable: se construye una vez y nunca cambia.

Como una foto o un ISO. Si quieres cambiarla, construyes otra.

⚙️

Contenedor

La imagen en ejecución. Un proceso aislado y desechable: se crea, corre y se destruye.

De una misma imagen puedes lanzar 1 o 500 contenedores idénticos.

🏛️

Registry

El repositorio de imágenes. Subes con push, descargas con pull.

Docker Hub, Artifact Registry, ECR. Es "el GitHub de las imágenes".

🔌

Puerto

El puente entre tu máquina y el contenedor, que por defecto está cerrado al mundo.

-p 8080:80 → tu 8080 entra al 80 interno del contenedor.

💾

Volumen

Almacenamiento que sobrevive al contenedor. Sin él, todo lo escrito adentro se pierde.

Imprescindible para bases de datos. Esta página no lo necesita.

La confusión #1 de la clase: imagen ≠ contenedor. La imagen es la receta de arepas; el contenedor es la arepa. Con una receta haces 50 arepas. Si se te quema una, botas la arepa — no la receta.

De un archivo de texto a una app corriendo en otro continente, en cuatro pasos.

☁️ La nube mismo artefacto, otro servidor
Aquí está la magia de la nube: el artefacto que despliegas es exactamente el que probaste en tu laptop. No se recompila, no se reconfigura, no se reinstala nada. Mismos bytes.

05

El Dockerfile de esta página, línea por línea

Este es el archivo real que construyó lo que estás viendo ahora mismo.

FROM nginx:1.27-alpine

Imagen base. Heredamos un Linux mínimo con Nginx ya instalado. Nunca partas de cero.

COPY app/ /usr/share/nginx/html/

Mete tus archivos dentro de la imagen. Desde aquí, la página vive en el contenedor.

EXPOSE 80

Documenta que el contenedor escucha en el 80. No publica nada por sí solo — eso lo hace -p.

HEALTHCHECK CMD wget … /health

Cómo saber si está sano. En producción, esto decide si te mandan tráfico o te reinician.

CMD ["nginx", "-g", "daemon off;"]

El proceso principal. Si muere, el contenedor muere. Debe correr en primer plano.

Cada instrucción crea una capa que Docker guarda en caché. Si solo cambias el HTML, no vuelve a descargar Nginx: reutiliza las capas anteriores. Por eso el segundo build tarda segundos y no minutos.
06

Comandos básicos

Haz clic en cualquier comando para copiarlo. Con estos ~15 sobrevives el 90% del tiempo.

🔨 Construir

docker build -t mi-app:1.0 .

Construye la imagen desde el Dockerfile. El . final es la carpeta de contexto.

docker images

Lista las imágenes que tienes en disco.

docker pull nginx:alpine

Descarga una imagen del registry sin ejecutarla.

▶️ Ejecutar

docker run -d --name web -p 8080:80 mi-app:1.0

Crea y arranca un contenedor. -d en segundo plano, -p publica el puerto.

docker ps

Muestra los contenedores corriendo.

docker ps -a

Muestra todos, incluidos los detenidos. Útil cuando "desapareció".

docker stop web

Detiene el contenedor (sigue existiendo).

docker start web

Lo vuelve a arrancar sin recrearlo.

docker restart web

Stop + start. Lo devuelve al estado original de la imagen.

🔍 Inspeccionar y depurar

docker logs web

Tu primer paso cuando algo falla. Muestra la salida del contenedor.

docker logs -f web

Sigue los logs en vivo, como tail -f.

docker exec -it web sh

Entra al contenedor con una terminal. Explora con ls, cat; sal con exit.

docker stats

CPU y memoria en tiempo real de cada contenedor.

🧹 Limpiar

docker rm web

Borra el contenedor (debe estar detenido).

docker rmi mi-app:1.0

Borra la imagen del disco.

docker system prune

⚠️ Borra todo lo que no esté en uso: contenedores detenidos, redes e imágenes huérfanas.

🎼 Docker Compose

Cuando ya no quieres memorizar flags, los escribes en un docker-compose.yml.

docker compose up --build

Construye y levanta todo lo definido en el archivo.

docker compose up -d

Igual, pero en segundo plano.

docker compose logs -f

Logs combinados de todos los servicios.

docker compose down

Detiene y elimina contenedores y redes del proyecto.

Regla mnemotécnica: build trabaja con imágenes, run crea contenedores, exec entra a uno que ya está corriendo. Si confundes run con exec, terminarás con 20 contenedores basura — muy normal al principio.
07

¿Y esto qué tiene que ver con la nube?

Todo. El contenedor es la unidad que la nube moderna espera recibir. Estos son los tres modelos de servicio y dónde encaja lo que acabas de hacer.

IaaS

Infraestructura

Te dan la máquina virtual vacía. Tú instalas el SO, Docker, la app y te encargas de parches y escalado.

EC2 · Compute Engine · Azure VM
PaaS

Plataforma

Entregas tu contenedor y la nube lo ejecuta, escala y asegura por ti. Aquí llega tu imagen.

Cloud Run · App Runner · Azure Container Apps
SaaS

Software

Solo lo usas desde el navegador. No hay servidor ni contenedor que administrar.

Gmail · Drive · Slack
Lo que hiciste hoy es local, así que todavía no es ninguno de los tres. Pero el salto a PaaS son literalmente dos comandos: docker push y desplegar. La imagen no cambia ni un byte.
08

Lo que acabas de hacer

  1. Escribiste un Dockerfile — la receta para construir la imagen.
  2. Construiste la imagen — docker build empaquetó SO, servidor y tu página.
  3. Corriste el contenedor — un proceso Linux aislado sirviendo esto que lees.
  4. Publicaste un puerto — 8080:80, por eso lo ves en el navegador.
  5. Verificaste su salud — el /health que consulta el HEALTHCHECK.

Siguiente paso: subir esta misma imagen a un registry y desplegarla en la nube. El archivo no cambia. Ese es exactamente el punto.
